4. MOD-001: Updated Odometer Reading Verification Workflow
4.1 Existing Situation / Current Status
At present, the odometer module allows the sales agent to upload odometer reading images. OCR extraction is used to read the
odometer value from the uploaded image. The application already shows a review/preview flow after image selection.
The current system is useful, but depending only on OCR may create issues in real field conditions because odometer photos
may be blurred, reflective, cropped, unclear, or captured in poor lighting conditions.
4.2 Proposed Change
The odometer workflow should be modified so that the sales agent must manually enter the km reading at the time of
uploading the odometer image. OCR will still extract the reading from the uploaded image and compare it with the agent-
entered reading.
If the difference between the agent-entered reading and OCR-extracted reading is within 1 km, the system should automatically
approve the agent-entered reading. If the difference is more than 1 km, or if OCR fails, the record should be automatically
forwarded to manager review.
4.3 Reason for Update
 OCR can make mistakes because of blurred images, analog odometers, poor lighting, reflection, cropped images, or dirty
vehicle dashboards.
 Agent-entered reading provides a human input value, while OCR acts as an automatic verification layer.
 The 1 km tolerance avoids unnecessary manager review for minor OCR differences.
 Manager review is only required when there is a meaningful mismatch, OCR failure, or image-quality issue.
 The workflow reduces fraud risk because agent-entered, OCR-extracted, and manager-final values are all stored for audit.
 The discard option prevents blurred or wrong images from entering system history or manager review queue.

4.7 New Discard Button Requirement

can immediately remove an unsuitable image and upload a fresh image before OCR or storage begins.

 If the image is cropped or the odometer is not fully visible, the agent can discard it.

 Discarded images shall not be saved in storage or Firestore.
 Discarded images shall not be processed through OCR.
 Discarded images shall not be forwarded to manager review.
 Discarded images shall not appear in odometer history.

5. MOD-002: GPS Watermark and Captured-Date Mapping Continuity
5.1 Existing Situation / Current Status
The application already uses OCR to read GPS/date watermark information from previously uploaded photos. When an older
odometer image is uploaded, OCR reads the GPS camera watermark and lists the reading as the reading for that captured date
instead of blindly treating it as the current upload date.
For live capture photos, the application already uses GPS watermark logic as well. This means the captured photo watermark,
GPS details, and date/time context are already part of the current odometer verification behavior.
5.2 Required Decision
This existing GPS watermark and captured-date mapping behavior must remain unchanged. The new manual-reading plus
OCR-comparison workflow must be added on top of the current GPS watermark logic, not replace it.
5.3 Reason for Keeping This Behavior
 Sales agents may upload previous-day odometer photos if they forgot to upload on the same day.
 GPS camera watermark helps identify the actual captured date and location of the odometer image.
 The system can correctly attach the odometer reading to the relevant day instead of the upload day.
 Live capture photos already follow GPS watermark verification, so the same behavior should continue for consistency.
 Retaining watermark reading improves audit accuracy and reduces false late-submission confusion.

GPS/date watermark extraction shall continue to support both previously captured photo uploads and live capture uploads. The

8. MOD-005: Same-Day START/END Uniqueness and Confusion Prevention
8.1 Loophole Identified
A potential loophole exists if a sales agent can upload multiple START readings and multiple END readings for the same
captured day or same workday session. This can confuse the system, create wrong distance calculation, and allow the agent to
choose a favorable reading later.
8.2 Opinion and Decision
This is a valid and important safeguard requirement. The system should not allow multiple active START or END readings for
the same agent and same captured workday/session. The application should maintain one authoritative START reading and one
authoritative END reading per agent per workday/session unless a manager formally reopens or corrects the reading.

 Active statuses should include OCR_PENDING, AUTO_CONFIRMED, CONFIRMED,

 Before accepting a new START or END submission, the API must check whether an active reading of the same type
already exists for that agent and captured day.
 If an active same-type reading exists, block the new upload and return the existing reading status to the UI.
 Allow re-upload only if the old reading is DISCARDED before final submit, REJECTED_BY_MANAGER, or
REOPENED_BY_MANAGER.
 Do not calculate reimbursement distance until exactly one final START and exactly one final END reading exist for the

8.6 Reason for Update
 Prevents agents from confusing the system with multiple START/END images for the same day.
 Prevents agents from later selecting the most favorable reading for reimbursement.
 Prevents accidental duplicate uploads from creating wrong distance calculation.
 Makes reimbursement calculation deterministic and audit-friendly.
 Forces corrections to happen through manager-controlled review instead of uncontrolled agent replacement.
8.7 Final Safeguard Rule
For each sales agent and captured workday/session, the system shall maintain only one active START reading and one active
END reading. Any additional same-type upload after final submission must be blocked unless the existing reading is rejected
or reopened by the manager. Distance and reimbursement shall be calculated only from the final approved START and final
approved END readings.

Version 1.3 Update: Additional Odometer and Reimbursement Lock Safeguards
Status: This section adds the new safeguards discussed after version 1.2. These controls prevent loopholes related
to past-image uploads, multiple readings for different captured dates, claimed reimbursement dates, paid claims,
and locked historical correction flows.
MOD-004: Captured-Date Based Past Image Upload Control
What to update: Past image uploads shall not be fully blocked. The system must identify the actual workday from
the GPS watermark or captured-date OCR and apply upload rules against that captured workday date, not only the
current upload date.
Why to update: Sales agents may forget to upload START or END readings on the same day. This rule keeps
genuine missed-day submission possible while still blocking duplicate or manipulated readings for the same
captured date.
Implementation rule: All odometer uniqueness, lock, reimbursement, and correction checks must use Agent ID +
Captured Workday Date + Reading Type, not Agent ID + Upload Date + Reading Type.
MOD-005: Multiple Past Readings Uploaded on the Same Day
What to update: An agent may upload multiple START or END readings on the same upload day only when those
images belong to different captured dates. The system must validate each image independently using its GPS
watermark/captured date.
Correct behavior: The current upload date should not be treated as the workday date.
 START for 10 May, START for 11 May, and START for 12 May uploaded on 15 May may be allowed if those
captured dates do not already have active START readings.
 A second START for the same captured date must be blocked or sent to manager replacement/correction flow.
 The system must not block a START upload merely because another START was uploaded on the same current
upload date.
MOD-006: Batch Past Upload Summary and Confirmation
What to update: When an agent uploads multiple past readings in one session, the application should show a batch
summary before final submission.
Preview summary should show: Captured date, reading type, agent-entered reading, OCR-extracted reading when
available, GPS watermark/date text, and any duplicate/lock warning.
Agent confirmation text: The agent should confirm: "I confirm these readings belong to the captured dates shown
above."
MOD-007: Incomplete Day Status
What to update: If only START or only END reading exists for a captured workday, that day must be marked as
incomplete.
Required status: Incomplete Day: START pending or Incomplete Day: END pending.
Why to update: Reimbursement calculation requires both START and END readings. Reimbursement must not be
allowed for incomplete days.
MOD-008: Reimbursement-Claim Lock for Odometer Readings
What to update: Once reimbursement has been submitted, approved, OTP-verified, or paid for a particular
captured workday, the agent must not be allowed to upload any new START or END reading for that same date in
normal flow.

MOD-009: Manager/Admin Reopen for Claimed Dates
What to update: If a correction is genuinely required after claim submission, only Manager/Admin should be able
to reopen that captured date. The agent must not directly reopen or modify claimed readings.
Reopen must capture: Reason for reopening, correction type, captured workday date, old START/END reading,
expected correction explanation, reopened by, and reopened at timestamp.
Correction mode rule: Reopen permission must be limited to one selected captured date and selected reading type
only. It should not unlock the agent for all old dates.
MOD-010: Paid Claim Should Not Be Directly Modified
What to update: If reimbursement is already paid, the original paid claim must remain locked. The system shall
not directly change the paid claim amount or distance.
Correct approach: Store the corrected reading as a new correction version, preserve the old record, calculate the
difference, and create a separate reimbursement adjustment entry.
 Earlier paid distance: 80 km; corrected distance: 90 km; adjustment = extra payable for 10 km.
 Earlier paid distance: 80 km; corrected distance: 70 km; adjustment = recovery/adjustment for 10 km in the
next claim.
MOD-011: Historical Reimbursement Period Lock
What to update: The system shall maintain a last reimbursement closed date for every agent. If a newly uploaded
image has a captured date earlier than or equal to this date, the upload must be blocked by default.
Required field: lastReimbursementClosedDate or lastPaidReimbursementDate per agent.
Rule: If Captured Date <= Last Reimbursement Closed Date, block upload. If Captured Date > Last
Reimbursement Closed Date, allow upload subject to normal START/END, OCR, duplicate, and manager-review
rules.
MOD-012: Locked Historical Date Correction Flow
What to update: For old locked dates, corrections must follow a controlled manager/admin reopen flow with audit
logging and adjustment handling. No historical paid or closed record should be directly edited.
Recommended flow: The locked-date correction process should follow these steps:
1. Agent attempts to upload a reading for an old captured date.
2. System checks captured date against lastReimbursementClosedDate and reimbursement status.
3. If the date is locked, the upload is blocked and the agent is instructed to contact the manager.
4. Manager/Admin reopens the selected captured date with a mandatory reason.
5. System allows correction upload only for that selected date and selected START/END type.
6. OCR and agent-entered reading comparison runs again.
7. Manager reviews old image, new image, old reading, OCR reading, proposed new reading, distance difference,
and reimbursement effect.
8. If approved and the claim is unpaid, the pending claim may be updated before payment.
9. If approved and the claim is already paid, a reimbursement adjustment entry must be created instead of
changing the old paid claim.

This section adds the two final clarifications discussed after version 1.3. These rules do not replace the existing

MOD-013: Missing GPS Watermark / Captured Date Manager Review Rule
Current status: The application already reads GPS/date watermark information from previously uploaded GPS

MOD-014: Odometer Continuity Check
Current status: Version 1.3 already includes previous reading comparison and daily START/END distance
validation. This section strengthens that rule by defining the exact continuity checks required between one final
approved reading and the next.
What to update: A new odometer reading must not be lower than the previous final approved reading for the same
agent/vehicle. Today’s START reading must not be less than the previous approved END reading, and today’s
END reading must not be less than today’s START reading.
Why to update: Odometers normally do not move backward. A backward reading may indicate a wrong image, old

reimbursement manipulation.
Required validation rules:
 New START reading must be greater than or equal to the previous final approved END reading for that agent/vehicle.
 END reading for the same captured workday must be greater than or equal to the START reading.
 If END is less than START, the system must block auto-approval and send the record to manager review.
 If the new reading is lower than the previous approved reading, the system must send the record to manager review with a
continuity warning.
 Manager approval must require a remark explaining why the continuity exception is accepted.
 The system must store previous reading, current proposed reading, difference, warning reason, manager remark, reviewed
by, and reviewed at timestamp.

30. MOD-030: Sales Agent Dashboard Map View for Existing Sites
This modification adds a Map View button in the Sales Agent Dashboard. When the sales agent clicks Map View,
the system should display existing sites as map markers so the agent can visually plan visits, identify nearby
opportunities, open directions, and avoid duplicate site creation. This is a dashboard planning feature and must not
be treated as proof of site visit.
30.1 Current Workflow / Current App Status
The application already stores lead, site, stakeholder, GPS/photo location data, site visit logs, and a Get Direction
feature. However, site visibility is mostly list/card based. A sales agent currently has to search or open sites
individually instead of seeing all assigned/existing sites on a map. This limits practical field planning, especially
when multiple sites are located in the same area.
30.2 Proposed Upgrade
Add a Map View button on the Sales Agent Dashboard. On clicking this button, the agent should see authorized
existing sites plotted on a map using their saved GPS coordinates. The map should support marker popups, Get
Direction, Add Site Visit, View Timeline, Request Quotation, and filtering by status or follow-up need.
30.3 Reason for Update
In RMC sales work, the sales agent may visit multiple nearby sites in one trip. A map-based view helps the agent
identify active sites, pending follow-ups, quotation sites, converted sites, and nearby opportunities. It also helps
reduce duplicate site creation because the agent can visually see that a nearby site already exists in the system.
